# 目标

Android 手机同时连接局域网和 VPN 时，模拟器公布的 SIP 地址应与平台访问模拟器的有效信令路径一致，使点播的 ACK 和后续 BYE 正常完成，无需用户关闭 VPN 或手动填写本机 IP。

# 已确认的问题

现场会话 Call-ID：`uac-1791868431366561000`。

1. 平台从局域网 `192.168.124.3` 向手机 `192.168.124.4:44992` 发送 INVITE。
2. 手机的 200 OK 在 Contact 中公布 `10.8.0.4:44992`（手机 VPN 地址）。
3. 平台按 Contact 向 `10.8.0.4:44992` 发送 ACK，实际出口转为 VPN，来源成为 `10.8.0.3`。
4. 模拟器仍要求 ACK 来源等于 INVITE 来源 `192.168.124.3`，以 `MismatchSource` 拒绝 ACK。

同一会话的 Call-ID 和双方 tag 对应正确。问题由模拟器公布的 Contact 改变了信令路径触发，修复应消除地址选择与会话来源要求之间的冲突。

上述地址和端口仅用于描述本次现场，不能成为固定配置或代码常量。

# 用户故事

- 作为同时使用 Wi-Fi 和 VPN 的用户，我希望通过局域网平台注册、点播和停止播放时，无需关闭 VPN。
- 作为通过 VPN 访问平台的用户，我希望模拟器继续使用可达的 VPN 信令路径。
- 作为选择 AUTO、WIFI 或 CELLULAR 网络偏好的用户，我希望修复保留各选项现有的网络选择语义。
- 作为使用独立媒体服务器的用户，我希望 SIP 走局域网、媒体走 VPN 的场景继续可用。

# 验收标准

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| AC-1 | 本次 Wi-Fi 与 VPN 并存拓扑，经局域网平台点播 | 200 OK Contact 公布手机局域网可达地址；若现场地址未变，应为 `192.168.124.4`，端口为实际 SIP 监听端口。平台 ACK 经局域网到达并被接受，不再出现本次 `MismatchSource`。 |
| AC-2 | ACK 接受后停止点播 | BYE 正常处理，会话及媒体资源按现有流程释放，不因 ACK 被拒绝触发超时清理。 |
| AC-3 | 仅局域网，无 VPN | 注册、点播、ACK 和 BYE 正常完成。 |
| AC-4 | SIP 平台实际通过 VPN 可达 | 模拟器公布 VPN 路径可达的 SIP 地址，注册及点播会话正常完成。 |
| AC-5 | 显式选择 WIFI 或 CELLULAR | 所选网络可用时，实际信令路径与公布地址一致；网络不可用时保持已有状态和提示语义。 |
| AC-6 | SIP 平台在局域网，媒体服务器 `192.168.10.220` 经 VPN 可达 | SIP 会话正常，媒体连接及实际出流正常；SIP 地址选择修复不能破坏媒体服务器的可达性。 |
| AC-7 | 无关来源发送 ACK | 保留现有会话身份及来源校验，不以无条件接受不同来源 IP 的方式绕过问题。 |
| AC-8 | 开启 VPN 前后分别新建会话 | 每个新会话使用当前有效的信令地址，不继续公布过期接口地址。 |

自动化回归和手机实测结果分别记录。源码测试通过不能代替手机报文和媒体验收；无法执行的场景明确标记为未验证。

# 范围与约束

- 修复 Android 模拟器的 SIP 本机地址选择及必要的地址传播行为。
- 保留显式网络偏好，支持局域网平台和 VPN 平台。
- 保留现有会话来源检查；不全局禁用 VPN，不新增要求用户手填本机地址的配置。
- 信令与媒体可能经过不同网络，分别满足各自的可达性要求。
- 保留仓库现有目录管理等无关改动。

# 非目标

- 修改平台 ACK 路由策略。
- 重做桌面或 iOS 网络架构。
- 扩展 SIP 身份安全校验、重构目录管理或 UI。
- 保证网络切换过程中已经建立的会话无缝迁移。

# 未决问题

- 技术方案阶段确认 Android 上如何可靠获得信令实际路径对应的本机地址，并兼容显式网络绑定。
- 技术方案阶段确认 SIP Contact 与 SDP 地址的使用边界，覆盖信令和媒体经过不同网络的情况。
- 任务阶段明确可自动化的回归用例和需要手机实测的场景；新增回归测试先复现缺陷，再验证修复。
